## 0. Стандарт v2 — головні принципи (обов'язкові)

Відгук учня: «багато води», «незрозуміло, що від мене хочуть і що буде викликатися», «задачі заради задач», «у темі про hoisting задача з Map, а Map ми не проходили», «якщо відповів неправильно — я нічому не навчився». Тому:

1. **Вчитися через задачі, а не через тексти.** Тема розбита на **кроки** (`groups: [{ id, title }]`) — це лише структура й прогрес, **без окремих уроків**. Нове поняття вводиться прямо в задачі, де воно потрібне: 2–4 рядки «**Як це працює:**» + крихітний приклад. Перші 1–2 завдання кроку знайомлять з ідеєю «через дію», далі — закріплення від простого до складного. Глибше учень читає за посиланнями теми (MDN/javascript.info), які застосунок показує сам.
2. **Без забігання наперед.** Завдання вимагає лише те, що пройдено в цьому та попередніх кроках і темах (порядок тем — у `data/_topics.js`). Наприклад, до теми `js-modern` — жодних `Map`/`Set` (використовуйте об'єкт/масив), базові `class`, `new` і `this` у методах вводяться в `js-start`; до `js-this` — жодних `call`/`apply`/`bind`, до `js-prototypes` — жодних `extends`/`super`/`prototype`, до `js-async` — жодних `Promise`/`async`. Перевірка: `node tools/check-prereqs.js <topic>`.
3. **Жодних задач заради задач.** Кожна задача з кодом — або **реально часта на співбесідах**, або **реальна ситуація з роботи фронтендера** (обробник кліків у циклі, кошик, форматування ціни, фільтр списку…). У тексті є рядок **«Де трапляється:»**. Штучні вправи без практичного сенсу — переписати на реальний сценарій або видалити.
4. **Зрозуміло, що робити і що буде викликатися.** Умова задачі — за шаблоном (нижче). Обов'язково видно: які функції/методи треба написати, які аргументи, що повертають, і приклад викликів з результатами.
5. **Помилка = навчання.** У квізах і теорії поле `why` — масив коротких пояснень **для кожного варіанту** (1 речення): чому правильний правильний і чому хибний хибний (і в чому правильна думка). Учень бачить це одразу після відповіді. `explanation` у квізі — коротко (до ~600 символів), без повторення `why`.
6. **Без води.** Короткі речення, списки, код. Не пояснюйте очевидне, не дублюйте одне й те саме в умові, уроці та поясненні.
7. **Від прикладу до самостійності (worked example → faded → independent).** Крок починається з розбору готового коду (квіз «що виведе»), далі — задача з майже готовим каркасом, далі — каркас лише з кроками-коментарями, наприкінці — задача з нуля. Для початківців так навчання йде помітно швидше, ніж із чистого аркуша.
8. **Факти — лише перевірені.** Внутрішня будова рушіїв і браузерів змінюється (наприклад, рівні компіляції V8). Що не підтверджено документацією (v8.dev, MDN, специфікація), формулюйте обережно («класично», «зазвичай») або не пишіть.
9. **Без дублікатів.** Перед новим завданням перевірте, чи тема вже є в модулі (`node tools/topic-map.js <topic>`): друге завдання на те саме має давати нову грань, а не повтор.
10. **Підручник поруч із практикою.** Кожен крок модуля має підрозділ у підручнику з такою самою назвою (`## <назва кроку>`); перевірка — `npm run book`. Нова тема канону — запис у `tools/syllabus.js`, перевірка — `npm run coverage`.

### Шаблон умови для `code` / `dom`

```markdown
**Завдання.** Одне-два речення: що зробити, простими словами.

**Де трапляється:** реальний сценарій або «класика співбесід (компанії часто просять…)».

**Що написати**
- `add(name, price, qty = 1)` → нічого не повертає; додає товар або збільшує кількість
- `total()` → число: сума `price * qty`

**Приклад**
```js
cart.add('apple', 10, 2);
cart.total(); // 20
```

**Як це працює:** 2–4 речення про механізм «під капотом», потрібний саме тут (чому замикання робить стан приватним тощо).

**Врахуйте:** крайові випадки списком (порожній ввід, повторне додавання, не мутувати вхідні дані…).
```

### Стартовий код — каркас, а не порожнеча

Стартовий код показує **структуру** рішення: сигнатури всіх функцій/методів, коментарі-кроки `// 1. …`, `// TODO`, а внизу — закоментований приклад, який можна виконати в консолі. Він **не містить рішення** і має провалювати тести.

```js
const cart = (function () {
  // 1. Приватний стан: оголосіть тут об'єкт для товарів.
  //    Ззовні IIFE до нього не дістатися — це і є «приватність».

  // 2. Поверніть об'єкт з методами — вони «бачать» стан через замикання.
  return {
    add(name, price, qty = 1) {
      // TODO: якщо товар уже є — збільшити qty, інакше створити запис
    },
    remove(name) {
      // TODO: видалити і повернути true, або false, якщо товару не було
    },
    total() {
      // TODO: сума price * qty
    },
    count() {},
    list() {
      // TODO: повернути КОПІЮ: [{ name, price, qty }]
    },
    clear() {}
  };
})();

// Спробуйте в консолі: cart.add('apple', 10, 2); cart.total()
```

## 1. Мова та стиль

- Увесь текст (умови, пояснення, відповіді, підказки) — **українською**. Код, імена змінних і функцій — англійською.
- Терміни, які на співбесідах звучать англійською, давайте в дужках при першій появі: «замикання (closure)», «спливання (bubbling)».
- Пишіть коротко й по суті, але **без прогалин**: краще конкретний приклад коду, ніж абзац абстракцій.
- Пояснення та відповіді мають звучати як відповідь сильного кандидата: структуровано, з прикладами, крайовими випадками, підводними каменями та компромісами (trade-offs).

## 2. Рівні складності (`level`)

| level | Назва | Що перевіряє |
|---|---|---|
| 1 | Junior | Базове знання: визначення, просте використання, синтаксис |
| 2 | Middle | Впевнене використання, типові пастки, найчастіші питання співбесід |
| 3 | Strong Middle | Глибоке розуміння «під капотом», хитрі випадки, поліфіли, trade-offs |
| 4 | Senior | Деталі специфікації, складні реалізації, архітектурні компроміси |

Орієнтовний розподіл у темі: ~20% L1, ~35% L2, ~35% L3, ~10% L4. Основна маса — **L2–L3**, бо мета — Strong Middle.

`interview: true` — лише для питань, які **справді часто ставлять на співбесідах** (≈20–35% завдань модуля; класика на кшталт event loop, замикань, CORS, `key` у React, `v-if`/`v-show`). Позначка, що стоїть на половині модуля, нічого не виділяє — валідатор попереджає, якщо її більше 45%.

### Модулі для конкретного фреймворку

У `data/_topics.js` модуль може мати `framework: 'react'` або `'vue'` (як частини фінального проєкту). Тоді, якщо учень обрав інший основний фреймворк, модуль не входить у готовність, план і пробну співбесіду — так само, як курс другого фреймворку.

## 3. Файл теми

Кожна тема — окремий файл `data/<topic-id>.js` (id тем див. у `data/_topics.js`):

```js
FE.topic('js-types', {
  intro: `...markdown-шпаргалка...`,
  items: [ /* завдання */ ]
});
```

- **Порядок `items` — це навчальний шлях.** Групуйте за підтемами і йдіть від простого до складного: спочатку теорія/квіз по підтемі, потім задачі з кодом. Користувач проходить тему зверху вниз.
- **`intro`** — шпаргалка теми (30–80 рядків markdown): ключові поняття, таблиці, короткі приклади коду, типові пастки. Те, що варто перечитати за 5 хвилин до співбесіди.

## 4. Типи завдань

### Спільні поля

| Поле | Обов'язкове | Опис |
|---|---|---|
| `id` | так | kebab-case, **глобально унікальний**, з префіксом теми: `types-typeof-null` |
| `type` | так | `code` \| `dom` \| `quiz` \| `theory` |
| `level` | так | 1–4 |
| `title` | так | Коротка назва (до ~60 символів) |
| `interview` | ні | `true`, якщо часто питають на співбесідах |
| `tags` | ні | масив рядків, наприклад `['closures', 'timers']` |

### `code` — написати код (виконується у Web Worker)

| Поле | Обов'язкове | Опис |
|---|---|---|
| `description` | так | Умова (markdown): що зробити, сигнатура, приклади вводу/виводу, обмеження |
| `starter` | так | Стартовий код: сигнатура функції + `// ваш код`. **Не має проходити тести** |
| `solution` | так | Еталонне рішення — чисте, ідіоматичне, з коментарями в неочевидних місцях |
| `tests` | так, ≥ 3 | Тести (див. розділ 6). Покривайте базовий випадок, крайові випадки, пастки |
| `hints` | так, 2–3 | Поступові підказки: 1) натяк на напрям, 2) підхід/алгоритм, 3) майже рішення |
| `explanation` | так | Після розв'язання: чому працює, складність O(...), альтернативи, типові помилки, **що інтерв'юер може спитати далі** |
| `testTimeout` | ні | мс на один тест (за замовчуванням 2000) |

Середовище `code`: **Web Worker** — немає `document`/`window` (є `globalThis`/`self`), є `setTimeout`, `Promise`, `fetch` (лише через `mockFetch`), `localStorage` (in-memory), `structuredClone`, `console`. Функції/класи з коду користувача оголошуються на верхньому рівні (`function x` / `const x` / `class X`) — тести бачать їх напряму.

**Не називайте функції учня так само, як хелпери тестів** (`expect`, `mockFn`, `deepEqual`, `format`, `input`, `click`…): у тестах хелпер «затінить» функцію учня. Тому в проєкті тест-раннера — `expectThat`, `createMock`.

### `code` + `runtime: 'ts'` — TypeScript

| Поле | Опис |
|---|---|
| `runtime: 'ts'` | код перевіряється `tsc --strict` (TypeScript 6) і транспілюється перед запуском |
| `starter`, `solution` | TypeScript-код (без `import/export` — виконується як скрипт) |
| `tests` | звичайні **JS**-тести виконання (`expect`), можна `[]` для чисто типових задач |
| `typeTests` | `[{ name, code }]` — TS-код, що перевіряється разом з кодом учня, але не виконується |

Тести типів:
```ts
type T1 = Expect<Equal<MyPick<Todo, 'title'>, { title: string }>>;   // типи мають збігатися ТОЧНО
// @ts-expect-error
formatPrice('100');                                                    // рядок нижче МАЄ давати помилку
```
`Equal`, `NotEqual`, `Expect` доступні глобально. Перетин `A & B` не дорівнює плоскому об'єкту для `Equal` — розплющуйте через `Simplify`. Синтетичний тест «Типи: код компілюється без помилок» додається автоматично. Сума `tests + typeTests` ≥ 3. Твердження про помилки й виведені типи в квізах перевіряйте реальним компілятором (`node_modules/typescript`), а не з пам'яті.

### `dom` — HTML/CSS/DOM у реальному браузері (sandbox-iframe 800×600)

| Поле | Обов'язкове | Опис |
|---|---|---|
| `description` | так | Умова |
| `html`, `css`, `js` | ні | Стартові версії трьох «файлів» (рядки; HTML — вміст `<body>`) |
| `editable` | так | Які файли редагує користувач: `['css']`, `['js']`, `['html']`, `['html','css']`… Перший — активна вкладка |
| `solution` | так | Об'єкт лише з редагованими файлами: `{ css: '...' }` або `{ js: '...' }` — **повний вміст файлу** |
| `tests` | так, ≥ 2 | Тести виконуються після `load`, мають доступ до DOM |
| `hints`, `explanation` | так | Як у `code` |

Важливо для `dom`:
- Діють стандартні стилі браузера (у `body` є `margin: 8px`) — порівнюйте позиції **відносно** контейнерів, а не абсолютно.
- Тести бачать глобальні функції/змінні зі `js` користувача.
- Тести виконуються **послідовно в одному документі**: якщо тест змінює DOM (видаляє елемент, клікає), враховуйте це в наступних тестах або відновлюйте стан.
- `localStorage`, `sessionStorage`, `document.cookie` працюють (in-memory поліфіли).
- Для перевірки `submit` використовуйте хелпер `submit(form)` → `{ fired, prevented }`.

### `dom` + `runtime: 'react'` — компоненти React 19

| Поле | Опис |
|---|---|
| `html` | `'<div id="root"></div>'` |
| `js` / `solution.js` | JSX-код; `import { useState } from 'react'` і `from 'react-dom'` підтримуються. Компонент `App` автоматично рендериться в перегляді |
| `editable` | `['js']` |

Хелпери тестів (додатково до DOM-хелперів): `mount(Component, props)` → `{ container, rerender(props), unmount() }`; `act(fn)` (React.act); `typeInto(input, value)` — введення, яке бачить React; `settle(ms)` — дочекатися таймерів, промісів і ефектів усередині `act`. Події, що змінюють стан: `await act(() => click(btn))`; асинхронні дії (`useActionState`, `useOptimistic`): `await act(async () => { submit(form); })`. Тести без JSX — `React.createElement`. Поведінку React у квізах перевіряйте запуском (React 19 у `vendor/react`), а не з пам'яті.

**React + TypeScript:** `lang: 'tsx'` у завданні — код учня перевіряє `tsc --strict` з `@types/react` 19 (вкладка `App.tsx`, підсвітка TS). Дозволені `typeTests` з JSX, наприклад `// @ts-expect-error\nconst bad = <Button variant="huge" />;` — вони дописуються в кінець файлу учня. `import type` і `{ type X }` в імпортах з `react` підтримуються. Тести виконання лишаються JavaScript (`React.createElement`).

### `dom` + `runtime: 'vue'` — компоненти Vue 3

| Поле | Опис |
|---|---|
| `html` | `'<div id="root"></div>'` |
| `js` / `solution.js` | один або кілька `.vue`-файлів; кожен файл починається рядком `<!-- file: Назва.vue -->`; модулі — `<!-- file: useЩось.js -->` (або `.ts`) з іменованими експортами. Без маркера весь вміст — `App.vue`. Імпорти: `'vue'`, `./Назва.vue`, `./модуль.js` |
| `editable` | `['js']` |

- Кожен компонент і кожен іменований експорт модулів доступні в тестах за іменем (`App`, `TodoItem`, `useFetch`); `Vue` — глобальний.
- Хелпери: `mount(Component, props?, slots?)` → `{ container, vm, setProps(p), unmount() }` (слоти — функції або рядки, слот-пропи приходять аргументом); `nextTick()`; `typeInto(el, value)` повертає проміс (`await typeInto(...)`); `settle(ms)` — таймери + оновлення DOM.
- DOM оновлюється асинхронно: після `click(...)` — `await nextTick()`. Події компонента — через пропи `onНазва: mockFn()`.
- Компіляція — офіційний `@vue/compiler-sfc`; помилки шаблону й скрипта показуються з номером рядка.
- `<script setup lang="ts">` і `.ts`-модулі перевіряє справжній `tsc --strict` з типами Vue 3 (макроси `defineProps`/`defineEmits` — глобальні, імпорт `./X.vue` — через шим). Результат — окремий тест «Типи: …» з номерами рядків редактора; дозволені `typeTests` (додаються в кінець скрипта `App` або першого типізованого файлу). Шаблони не перевіряються — у проєктах це робить `vue-tsc`.
- Типи для type-based props оголошуйте в тому самому `<script setup>`: компілятор SFC у браузері не читає типи з інших файлів.
- Компоненти з `Teleport` і слухачами на `document` наприкінці тесту розмонтовуйте (`m.unmount()`).

### `quiz` — питання з варіантами відповіді

| Поле | Обов'язкове | Опис |
|---|---|---|
| `question` | так | Питання (markdown). Для «що виведе код» — блок коду |
| `options` | так | 2–6 варіантів (markdown-рядки, короткі). Вивід коду — у бектиках |
| `answer` | так | Індекс правильного варіанту (з 0) **або масив індексів** для кількох правильних |
| `hint` | так | Одна підказка, яка наводить на думку, але не видає відповідь |
| `explanation` | так | Чому правильна відповідь правильна **і чому інші — ні**. Покроковий розбір для коду |

- Варіанти **перемішуються під час показу** (при кожному відкритті й повторній спробі), тож позиція в даних ні на що не впливає. Тому варіанти не повинні посилатися на свою позицію («усі вище», «варіант A»); літери в тексті варіантів можуть лише називати позначки з коду питання («A і C — помилки»).
- Не посилайтеся на варіанти літерами («варіант Б»), посилайтеся на зміст.
- Неправильні варіанти мають бути **правдоподібними** (типові помилки мислення), а не абсурдними.
- Для множинного вибору починайте питання з «Оберіть **усі** …».

### `theory` — питання співбесіди з варіантами відповіді та розгорнутим поясненням

Користувач обирає варіант(и) відповіді, система перевіряє, а після перевірки показує ключові пункти, еталонну розгорнуту відповідь і уточнювальні питання.

| Поле | Обов'язкове | Опис |
|---|---|---|
| `question` | так | Питання так, як його ставить інтерв'юер |
| `choices` | так | 3–6 варіантів відповіді (markdown-рядки). Це **змістовні твердження**, що перевіряють розуміння суті питання, а не «так/ні» |
| `correct` | так | Індекс правильного варіанту **або масив індексів** (тоді у `question` додайте «Оберіть **усі** правильні твердження») |
| `answer` | так | Еталонна відповідь сильного кандидата (markdown, ≥150 символів): визначення → як працює → приклад коду → нюанси/пастки → коли застосовувати |
| `keyPoints` | так, 3–6 | Чекліст: що **обов'язково** має прозвучати у відповіді |
| `followUps` | ні | 2–4 уточнювальні питання, які інтерв'юер поставить далі |
| `hint` | ні | Підказка-напрям |

Правила для `choices`:
- Неправильні варіанти — **типові хибні уявлення** кандидатів (те, що реально кажуть на співбесідах), правдоподібні й конкретні.
- Варіанти **приблизно однакової довжини та стилю**: правильний не має вирізнятися детальністю (валідатор попереджає, якщо в темі правильний варіант часто найдовший).
- Без «усе вище перелічене» / «жоден»: варіанти перемішуються.
- Для широких питань («що таке X і навіщо») зручно множинний вибір з 4–5 тверджень, з яких 2–3 правильні.
- Розгорнуте `answer` залишається поясненням: після перевірки воно пояснює, чому правильне — правильне.

## 5. Markdown

Підтримується: абзаци, `## заголовки`, **жирний**, *курсив*, `inline code`, блоки коду з мовою (```js, ```html, ```css, ```text, ```http), списки (`-`, `1.`), таблиці (`| a | b |`), цитати (`>`), посилання `[текст](url)`, `---`.

### Екранування в шаблонних рядках

Довгі поля пишіть у шаблонних рядках `` `...` ``. Усередині:
- бектик → `` \` `` (тобто inline-код пишеться як `` \`map\` ``, а блоки коду як ` \`\`\`js `);
- `${` → `\${`;
- `\n` у **коді** (наприклад, рядок `'a\nb'` у `solution`) → `\\n`, інакше це стане реальним переносом рядка;
- аналогічно `\d`, `\s` у регулярних виразах → `\\d`, `\\s`.

Для коротких полів зручніше звичайні лапки `'...'` з `\n` для переносів — це особливо зручно в `tests`.

## 6. Тести

Тест — це рядок (тоді він же і назва) або `{ name, code }`. `code` — тіло **async-функції**: можна писати `await`. Назва — українською, описує вимогу: `'повертає [] для порожнього масиву'`.

```js
tests: [
  'expect(sum(1, 2)).toBe(3)',
  { name: 'не мутує вхідний масив', code: 'const a = [3, 1, 2];\nsortCopy(a);\nexpect(a).toEqual([3, 1, 2]);' },
  { name: 'чекає 100 мс', code: 'useFakeTimers();\nconst p = delay(100);\nadvanceTimersByTime(100);\nawait expect(p).resolves.toBeUndefined();' }
]
```

### `expect(value)` — матчери (Jest-сумісні)

`toBe`, `toEqual` (глибоке, ігнорує `undefined`-властивості), `toStrictEqual` (глибоке + прототипи), `toBeTruthy`, `toBeFalsy`, `toBeNull`, `toBeUndefined`, `toBeDefined`, `toBeNaN`, `toBeGreaterThan`, `toBeGreaterThanOrEqual`, `toBeLessThan`, `toBeLessThanOrEqual`, `toBeCloseTo(n, digits=2)`, `toContain` (масив/рядок/Set — за `Object.is`), `toContainEqual`, `toHaveLength`, `toHaveProperty(path, value?)`, `toMatch(regex|string)`, `toMatchObject`, `toBeInstanceOf`, `toBeTypeOf('string')`, `toSatisfy(fn)`, `toThrow(msg|regex|ErrorClass?)` (приймає функцію), `toHaveBeenCalled`, `toHaveBeenCalledTimes`, `toHaveBeenCalledWith`, `toHaveBeenLastCalledWith`.

Модифікатори: `.not`, `.resolves`, `.rejects` (з `await`!):
```js
await expect(promise).resolves.toEqual({ id: 1 });
await expect(promise).rejects.toThrow('HTTP 404');
```

`toEqual` порівнює `Map`, `Set`, `Date`, `RegExp`, масиви, об'єкти; циклічні посилання підтримуються.

### Хелпери

| Хелпер | Опис |
|---|---|
| `mockFn(impl?)` / `jest.fn()` | Шпигун: `.mock.calls`, `.mock.results`, `.mock.contexts` (this), `.callCount`, `.mockReturnValue(v)`, `.mockReturnValueOnce(v)`, `.mockImplementation(fn)`, `.mockResolvedValue(v)`, `.mockRejectedValue(e)`, `.mockClear()` |
| `useFakeTimers(start=0)` | Підміняє `setTimeout/setInterval/clear*`, `Date.now`, `performance.now`. **Автоматично скидається після кожного тесту** |
| `advanceTimersByTime(ms)` | Просуває фейковий час, виконуючи таймери по черзі |
| `runAllTimers()`, `runOnlyPendingTimers()`, `getTimerCount()` | Керування фейковими таймерами |
| `flushPromises()` | `await flushPromises()` — дочекатися виконання мікрозадач/промісів (працює й з фейковими таймерами) |
| `sleep(ms)` | Реальна пауза (уникайте > 100 мс; краще фейкові таймери) |
| `mockFetch(handler)` | Підміняє `fetch`. `handler(url, init)` повертає дані (→ JSON 200), або `{ status, body, headers, delay }`, або `Error` (мережева помилка). Підтримує `AbortSignal`. Повертає mockFn. Скидається після тесту |
| `getLogs()`, `clearLogs()` | Масив рядків, виведених через `console.*` |
| `deepEqual(a, b)`, `format(v)` | Утиліти |
| `assert(cond, msg)` | Проста перевірка |

Лише для `dom`:

| Хелпер | Опис |
|---|---|
| `$(sel)`, `$$(sel)` | `querySelector` / масив `querySelectorAll` |
| `css(elOrSel, prop)` | Обчислене значення CSS (`getComputedStyle`), наприклад `css('.box', 'display')` → `'flex'` |
| `rect(elOrSel)` | `getBoundingClientRect()` |
| `click(elOrSel)` | Клік зі спливанням; повертає подію (можна перевірити `defaultPrevented`) |
| `input(elOrSel, value)` | Встановлює `value` і генерує `input` + `change` |
| `press(elOrSel, key, init?)` | `keydown` + `keyup`; повертає `keydown`-подію |
| `dispatch(elOrSel, type, init?, Ctor?)` | Довільна подія |
| `submit(form)` | `requestSubmit()` → `{ fired, prevented }` |
| `nextFrame()` | Дочекатися двох кадрів `requestAnimationFrame` |
| `waitFor(() => cond, timeout=1000)` | Чекати, поки умова стане truthy |

### Правила якісних тестів

1. **Детермінованість.** Жодних реальних мережевих запитів і випадковості. Час — через `useFakeTimers()`.
2. **Швидкість.** Тест < 200 мс. Перевірки складності — через великі входи (наприклад, 10⁵ елементів), але без зависань рішення.
3. **Перевіряйте поведінку, а не реалізацію** — крім випадків, де вимога саме в реалізації (наприклад, «не мутуйте вхідний масив», «використайте делегування»).
4. **Крайові випадки:** порожній ввід, один елемент, від'ємні числа, `null`/`undefined`, дублікати, великі дані, `this`, повторні виклики, помилки.
5. Стартовий код **має провалювати** щонайменше один тест (валідатор це перевіряє).
6. Тести незалежні: не покладайтеся на стан після попереднього тесту (у `code`). Код користувача виконується **один раз** на запуск, тож його глобальний стан спільний для всіх тестів.
7. Хелпери (`expect`, `sleep`, `input`, `format`…) передаються в тест **параметрами**, тож функція користувача з таким самим ім'ям їх не зламає. Але тест тоді не зможе викликати функцію користувача з таким ім'ям, тож не називайте так функції в умові.
8. Ліміт часу тесту (`testTimeout`, за замовчуванням 2000 мс) перевіряється і для синхронного коду: тест, що виконувався довше, вважається проваленим. Для перевірок складності краще явно міряти `performance.now()` і давати запас.
9. Після `advanceTimersByTime()` колбеки промісів ще не виконані: у багатокрокових асинхронних сценаріях чергуйте `advanceTimersByTime(...)` і `await flushPromises()`.
10. У `dom`-задачах документ має origin `null`: `history.pushState` недоступний (використовуйте `location.hash`), а `AbortSignal.timeout()` не реагує на фейкові таймери.
11. Не оголошуйте в тестах змінні з іменами хелперів (`const $ = …`, `input`, `format`): хелпери — параметри функції тесту, повторне оголошення дає SyntaxError.
12. Стан модуля (стори, реєстри) спільний для тестів одного запуску: скидайте його на початку тесту (`setActivePinia(createPinia())`, `auth.loggedIn = false`).
13. Нові API мови (Temporal, iterator helpers, `using`) перевіряйте у валідаторі й зазначайте в умові мінімальні версії браузерів.

## 7. Перевірка

```bash
node tools/validate.js <topic-id> [<topic-id> ...]
```

Валідатор у справжньому Chrome перевіряє схему, запускає **еталонне рішення** (усі тести мають пройти) і **стартовий код** (хоча б один тест має впасти). Робота вважається завершеною лише коли для ваших тем: `помилок: 0`.

Еталонні приклади всіх типів: `tools/examples.js` (`node tools/validate.js --examples`).
